# 参考产品录屏分析：NFC「碰一碰传图」（OPPO 互传）

> 本文是对一段 29.87s 的双机演示视频的逐帧分析，用于复刻参考产品的**流程与交互设计**（不涉及实现）。
> 所有结论均标注帧号，可按下文「附录 A」的命令逐条复查。

- 素材：`Temp/video.mp4`（只读，未改动）
- 规格：29.87s / 540x960 竖屏 / 30fps / 含音轨（AAC 44.1kHz 立体声）
- 抽帧：2fps 共 60 帧 → `_Temp/frames/f_0001.jpg .. f_0060.jpg`，**帧号 N ↔ 时刻 t=(N-1)/2 秒**
- 本文中所有帧引用写作 `f_0012.jpg (t=5.5s)` 形式
- 分析用工作文件均在 `_Temp/` 下（`verify/`、`top_rot/`、`audio.wav`、`spectrogram.png`）

---

## 0. 一句话结论

被演示的产品是 **OPPO 互传**。核心交互是：

> 两台手机**屏幕朝上并排摆放、各自的"顶边"（NFC 天线端）相互靠近**触发连接 →
> **当前正在看图的那台手机**弹出「发送给 <对方设备名>」面板，提示「**上滑发送 1 张照片**」；
> 用户上滑后，**对方手机**弹出「来自 <本机昵称> 的分享」卡片，带【接收 1 张照片】【拒绝】两个按钮；
> 对方点「接收」→ 传图完成；点「拒绝」→ 发送方顶部弹出红色失败提示「发送失败 / 对方拒收」。

全片共演示**两轮**：第一轮"接收成功"，第二轮"被拒收"，两轮角色互换。

## 1. 演示环境与两台手机

### 1.1 物理摆位（关键且容易被忽略）

两台手机**都屏幕朝上**平放在白色桌面上，**上下相邻、顶边对顶边**：

```
        录制视角（540x960）
   ┌───────────────────────────┐
   │        ┌───────────┐      │   ← 上方手机（A）
   │        │  屏幕倒置 │      │      整机在画面里旋转了 180°：
   │        │  ▲顶边朝下│      │      它的"顶边"朝向画面下方
   │        │           │      │
   │        └───────────┘      │
   │            ‖ ‖            │   ← 两台手机的"顶边"在此贴合
   │        ┌───────────┐      │      （NFC 天线对天线）
   │        │  ▲顶边朝上│      │   ← 下方手机（B）
   │        │  屏幕正置 │      │      整机在画面里正立：
   │        │           │      │      它的"顶边"朝向画面上方
   │        └───────────┘      │
   └───────────────────────────┘
```

- **上方手机（下称 A）的屏幕内容在画面里是倒的**。证据：`f_0002.jpg (t=0.5s)` 中 A 的状态栏（时钟/4G/电量）出现在手机屏幕的**下沿**，桌面 dock 出现在屏幕**上沿**；对 A 的截图区域做 `hflip,vflip`（旋转 180°）后，主屏、状态栏、弹窗文字全部正立可读。
  - 反过来验证：不旋转直接读 A 的对话框只能得到倒字；旋转后 `f_0034.jpg (t=16.5s)` 的权限弹窗完全可读（见 §4.4）。
- **下方手机（下称 B）正立**，无需旋转。
- **两台手机顶边相对** 正是 NFC 天线对天线的物理要求，也是本演示摆位的成因；复刻时若要拍同样的演示片，必须复现这个"反向摆放"。

### 1.2 两台手机的身份

| | 上方手机 A | 下方手机 B |
|---|---|---|
| 画面朝向 | **倒置 180°** | 正立 |
| 机身 | 墨绿/深灰边框，水滴屏 | 酒红/绛红边框，水滴屏 |
| 导航方式 | **三键导航**（返回/桌面/多任务） | 手势导航（无导航栏） |
| 设备名（对端可见） | **`U119652157`** | **`一路有云`**（4 个汉字，逐字不完全确定） |
| 演示初态 | 桌面（壁纸为森林人像） | 照片查看器（人像照片全屏） |

设备名证据：
- `f_0046.jpg (t=22.5s)` B 顶部标题「**发送给 U119652157**」→ B 要发给 A，所以 A 的名字是 `U119652157`（6x 放大后可读，中段数字 `119652157` 有 ±1 位不确定）。
- `f_0017.jpg (t=8.0s)` A 顶部标题「**来自 一路有云 的分享**」→ A 收到来自 B 的分享，所以 B 的名字是「一路有云」（4 字，字形辨识度低，可能为「一踏青云 / 一路青云」等近似字）。
- 两个名字在全片**始终一致**，是判定角色互换的关键锚点。

## 2. 角色判定：A / B 在两轮中互换

这是本片最容易误判的地方 —— **不是"一台永远发、一台永远收"，而是每轮由"谁先上滑"决定角色**。

| 轮次 | 时间 | 发送方 | 接收方 | 结局 |
|---|---|---|---|---|
| 第一轮 | t≈3.0s – 19.0s | **B（下方）** | **A（上方）** | **接收成功** |
| 第二轮 | t≈21.0s – 29.9s | **A（上方）** | **B（下方）** | **被拒收 → 发送失败** |

判定依据（都是"谁的面板写『发送给』、谁的面板写『来自…的分享』"）：

- 第一轮：`f_0011.jpg (t=5.0s)` B 显示「发送给 U119652157」+「↑ 上滑发送 1 张照片」；`f_0017.jpg (t=8.0s)` A 显示「来自 一路有云 的分享」+【接收 1 张照片】【拒绝】。→ **B 发 A 收**。
- 第二轮：`f_0048.jpg (t=23.5s)` A 显示「发送给 一路有云」+「↑ 上滑发送 1 张照片」；`f_0052.jpg (t=25.5s)` B 显示「来自 U119652157 的分享」+【接收 1 张照片】【拒绝】。→ **A 发 B 收**。

### 2.1 一个重要的对称设计发现

⚠️ `f_0046.jpg (t=22.5s)`：**两台手机同时都在显示「发送给 <对方>」面板**——
A 显示「发送给 一路有云」，B 显示「发送给 U119652157」。

也就是说：**碰一碰之后，凡是"当前正在看图"的手机都会亮出发送面板**（谁都可以发），
**谁先上滑谁就成为发送方**，另一台随即把面板切换成「来自…的分享 / 接收 / 拒绝」卡片。

第一轮之所以只有 B 有面板，是因为**A 当时停在桌面、没有正在浏览的照片**，无内容可发。
第二轮 A 打开了相册看图，于是双方都亮出了面板。

> 复刻要点：这不是"主从"模型，而是**对等的"先动手者为发送方"**模型。

## 4. 交互编排（分步）与每个 UI 界面的精确描述

### 4.0 编排总览

```
第一轮（成功路径）
  ①把两台手机顶边推到一起（~0.5s）
      └─ 发送方 B 屏幕顶边浮出蓝紫光晕
  ②B 出现「发送给 <A>」+「↑上滑发送 1 张照片」          ← 发送方要动一次手
  ③B 上滑  →  A 弹出「来自 <B> 的分享」+【接收 1 张照片】【拒绝】   ← 接收方要动一次手
  ④A 点「接收 1 张照片」 → 按钮消失、照片留下 → 回到桌面
  ⑤（一次性）首次启动授权：用户须知 → 权限弹窗
第二轮（拒绝路径）
  ⑥A 打开相册看刚收到的照片
  ⑦再次碰一碰 → 双机同时出现发送面板
  ⑧A 上滑（触发传送，出现粒子动画）
  ⑨B 弹出接收卡片，B 点「拒绝」
  ⑩A 顶部出现「发送失败 / 对方拒收」（驻留到片尾）
```

**关键：整个过程需要两方各确认一次**（发送方上滑 + 接收方点按钮），不是"一碰即传"。

### 4.1 发送方面板（B 第一轮 / A 第二轮）

| 项 | 内容 |
|---|---|
| 出现时机 | 碰一碰后 ~0.5–1.0s（`f_0008.jpg (t=3.5s)` 先出光晕，`f_0009.jpg (t=4.0s)` 出面板） |
| 顶部 | 一条**自上而下的深色渐变**遮罩，压在原照片上；正中白字「**发送给 U119652157**」（对端设备名） |
| 中部 | 照片变**圆角卡片**（不再是满屏），左右留黑、背景压暗 |
| 卡片下方 | 一行白字提示：「**↑ 上滑发送 1 张照片**」（↑ 为向上箭头图形，其后为"上滑发送 N 张照片"，N 为张数） |
| 最底部 | 一个图标 + 「**一键互联**」（OPPO 互传的品牌语），居中且字号最小 |
| 用户动作 | **在照片上向上滑动**（不是点按钮，没有按钮） |
| 消失时机 | 会话结束后自动消失（第一轮在 t≈19.0s 前已消失，见 `f_0039.jpg (t=19.0s)` 回归纯照片查看器） |

### 4.2 接收方卡片（A 第一轮 / B 第二轮）

| 项 | 内容 |
|---|---|
| 出现时机 | 发送方上滑后 ~0.5s（`f_0014.jpg (t=6.5s)` 入场，`f_0015.jpg (t=7.0s)` 成形） |
| 顶部 | 白字「**来自 一路有云 的分享**」（发送方昵称 + "的分享"） |
| 中部 | 照片卡片（圆角，未点接收前**已能看到照片预览**） |
| 按钮 1 | **白色胶囊按钮**：「**接收 1 张照片**」（含张数） |
| 按钮 2 | **深灰半透明胶囊按钮**：「**拒绝**」 |
| 最底部 | 与发送面板相同的「**一键互联**」品牌行 |
| 背景 | 卡片背后是**被虚化的桌面**（发送方 A 的第一轮里，背景是它原本的桌面） |

| 接收后 | `f_0020.jpg (t=9.5s)`：两个胶囊**整体消失**，只留照片；随后 `f_0021.jpg (t=10.0s)` 回到桌面 |

> 注意：**卡片顶部没有关闭 ✕**，只有「拒绝」一个退出路径。

### 4.3 相册 / 照片查看器（A 第二轮，也是 B 全程的表情）

- **A 的相册**（`f_0041.jpg (t=20.0s)`、`f_0044.jpg (t=21.5s)`、`f_0059.jpg (t=29.0s)`）：
  - 顶栏：`←` 返回 + 「**今天**」+ 时间「16:07」；右上 `⋯`
  - 底部工具条（5 个图标）：`↗`(分享) `♡`(收藏) `✏️`(编辑) `🗑️`(删除) `ⓘ`(信息)
  - 系统三键导航（返回/桌面/多任务）常驻
  - 传送期间状态栏出现「**等待发送**」（`f_0052-f_0055`，字号极小，**推断**）
  - 这就是"**在图库里看图时碰一碰**"的入口场景：图片应用本身就是发送入口，**不需要先打开某个互传 App**
- **B 的照片查看器**（`f_0001`–`f_0008`、`f_0039`）：照片上下留黑的沉浸式查看器，**无任何工具条/标题**，与 A 的相册不是同一个 App（B 是第三方/简易查看器，A 是系统相册）

### 4.4 首次启动的两个对话框（A，t=10.5–17.0s）

这是 demo 机上 OPPO 互传**首次启动**的授权流程，一次性的，**不属于日常碰一碰路径**，但复刻时建议保留（因为它出现在"接收动作之后"，说明**接收落盘需要相册权限**）。

## 8. 复刻必须做对的「手感」要点

1. **两方各确认一次**：发送方「上滑」+ 接收方「点按钮」，缺一不可。不是一碰即传。
   - 发送方**用滑动而非按钮**（提示语「↑ 上滑发送 1 张照片」），接收方用**两个明确胶囊按钮**。
   - 这种"发送方滑、接收方点"的不对称是刻意设计：滑动有"推出去"的语义，点按钮有"接住"的语义。
2. **对等而非主从**：两台都在看图时，**两台都亮出发送面板**；谁先动手谁是发送方，另一台**随即切换**为接收卡片（`f_0046` → `f_0051`，同一台手机从「发送给 X」变成「来自 X 的分享」）。复刻时若写成固定主从会明显走味。
3. **无内容的设备不打扰**：A 停在桌面时碰一碰，A 屏上**什么都不发生**（第一轮 A 在 f_0009–f_0013 毫无变化）。接收通知只在对方真正"发送"时才出现。
4. **必须报出对端身份**：发送方标题带**对端设备名**（"发送给 U119652157"），接收方标题带**发送方昵称**（"来自 一路有云 的分享"）。带张数的文案（"1 张照片"）也要有。
5. **照片预览先到、确认后到**：接收卡片里在点确认**之前**就已显示完整照片（`f_0015.jpg (t=7.0s)`）。确认只决定"接不接收/落不落盘"。
6. **连接反馈要贴在"接缝"上**：光晕出现的**方位**就是对方的方位（各自朝内的那条边），且是**彩虹色**而非单色。
7. **成功要安静、失败要高调**：成功无任何 toast，只有"按钮消失"；失败是顶部红色横幅 + 归因文案「对方拒收」，且**不自动消失**。
8. **卡片/弹窗一律带背景虚化**，且用圆角大卡片 + 胶囊按钮的语言（接收方是两个胶囊：白=主操作、深灰=次操作/拒绝）。
9. **底部品牌行「一键互联」** 在发送面板和接收卡片上都出现，字号最小、居中 —— 是品牌位而非功能位。
10. **入口是图片应用本身**：第二轮 A 是在**系统相册里看图**直接碰一碰发出的，**没有先打开"互传 App"**。复刻时应把碰一碰能力挂在图库/查看器上。
11. **拒绝是一条正式路径**，有完整的对端反馈闭环（不是静默丢弃）。
12. **导航/状态栏差异属演示机差异**：A 用三键导航、B 用手势；这类系统级差异不必跟随。
